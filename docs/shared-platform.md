# 项目组共享模型平台设计

本文件区分已实现的本地 MVP 与后续设计，不记录任何实际部署地址、身份、凭证或资产。

## 主线与边界

成员客户端通过 Base URL 找到网关，通过独立 Bearer API Key 证明身份，通过 model 字段选择已授权的逻辑模型。网关校验身份、模型范围、容量和预算，将逻辑模型映射到管理员维护的上游地址，再由推理服务加载权重执行。成员 Key 不等于上游 Key；Key 不绑定一张独占 GPU。模型参数由推理服务解释，平台只允许显式支持的协议。

已实现：独立 Key、后端角色与模型/profile 授权、用户/Key 预算、非流式 Chat Completions、幂等、对账、视频模拟队列、独立模拟控制代理、工具子入口，以及资源预约登记/审批/排程与个人通知。尚未实现：完整 Agent 协议、正式账号会话、预约自动执行、文本离线作业、真实 GPU 执行器、夜间自动切换和公网部署。

## 权限矩阵

| 操作 | admin | operator | caller | auditor |
|---|---|---|---|---|
| 已授权模型调用、自己的任务/结果 | 是 | 是 | 是 | 否 |
| 创建成员、发 Key、调整预算 | 是 | 否 | 否 | 否 |
| 修改运行策略 | 是 | 否 | 否 | 否 |
| 执行运行操作 | 是，需 profile grant | 是，需 profile grant | 否 | 否 |
| 读运行清单与审计 | 是 | 是 | 否 | 是 |
| 读取其他用户正文/产物 | 不因角色自动获得 | 否 | 否 | 否 |
| 查看项目工具入口 | 是 | 是 | 是 | 是 |

当前为单组角色，API Key 继承所属用户角色；管理员 Key 具有管理权限，应与普通调用账号分开。正式上线前需独立 Web 登录会话与仅可推理的 Key scopes，加入组/项目资源范围及受控邀请。未来“申请切换模型”是成员权限，“批准预约”是管理员权限，“执行切换”是操作员权限，不能合并为选择模型的副作用。工具入口当前组内可见，原站负责其内部访问控制；尚无统一登录或逐工具授权。

## 单个大模型常驻与预约

模型目录保存所有已登记模型，并分别展示 installed、approved、ready、draining、stopped 等状态。只允许 ready 路由接收即时请求；列表可见不代表当前可调用，也不代表获得运行操作权限。不把未运行模型静默替换成另一个模型。

拟议工作流：成员申请模型及用途/预估任务量 → 管理员批准时间窗（Asia/Shanghai）及资源预算 → 调度器合并同模型作业 → 提前公告并阻止新的即时派发 → 等待在途任务排空 → 受限代理停旧 profile → 核对资源锁 → 启动批准的新 profile → 健康检查通过才切路由 → 执行作业 → 持久化结果 → 按策略恢复常驻模型。超时不强杀既有业务，交由操作员决定；启动失败恢复旧路由/模型并记录审计。已下载权重与镜像不删除。

v0.4.0 已实现上述流程的预约申请、管理员时间窗/显示顺序和站内通知部分。之后的模型切换、任务执行和结果收集仍未接入；预约批准不是执行成功，也不允许绕过实际调用时的权限和额度检查。

调度需要维护窗口长度、最长排空时间、最大等待时间、最小驻留时间、防饥饿、公平份额和失败退避；单有“北京时间凌晨”条件不足以批准停机。真实启停器接入前，这些都是设计，不会自动执行。

## 客户端关闭后的任务

普通 Chat Completions 是一次实时 HTTP 交互，不能让连接等待一夜。离线模型请求应使用独立的持久化作业协议（拟议 POST /api/jobs 返回 202 与 job_id，GET /api/jobs/{id} 查询，GET /api/jobs/{id}/result 取结果），并要求所有接口检查归属。状态包括 pending_approval、waiting_model、queued、running、succeeded、failed、cancelled、unknown；任务绑定模型版本、输入快照、幂等标识、计费规则版本、过期时间和批准预算。未执行任务不宜整夜冻结全部即时额度，执行时再次检查授权和原子预留。

服务端 worker 执行完整的纯模型作业，结果入库，用户下次打开后取回。仅关闭界面而后台进程仍运行的 harness 可能继续工作，必须以客户端实际行为为准；完全退出客户端后，它的文件读取、Shell、后续模型请求和人工确认不会被网关自动接管。

若希望 Agent 整夜完成任务，需要仍运行的客户端守护进程，或带隔离工作区、工具权限、人工确认检查点和恢复日志的服务端 harness。平台不会因为保存了一条模型回复，就声称完成了客户端的完整 Agent 工作流。

## 并发与额度

网关异步处理网络请求，SQLite WAL 支持并发读取、串行短写事务；数据库事务内不等待模型。推理引擎在有限 GPU/KV cache 容量内批处理多个请求。平台限制用户/Key 并发、RPM、估算 TPM 与全局容量，超限返回明确错误或进入有界队列，避免无限堆积。持久化视频模拟队列不能当成已实现的文本预约系统。

每次模型请求预留输入估算加最大输出预算，再按可信 usage 结算并释放余量。Agent 一个任务通常包含多次模型请求，只保证这一请求的额度，不保证整条任务无限继续。网络中断后的未知提交不盲目重试；缺失 usage 保留待对账，防止重复执行/扣费。当前按 UTF-8 字节加余量保守估算，生产前需匹配 tokenizer 校准。

## 客户端配置与当前兼容性

本地 Base URL 为 http://127.0.0.1:8765/v1；model 为管理员公布的模型 ID；API Key 使用成员账号下的调用凭证。地址选择由运行客户端的机器是否能访问决定。

DeepSeek Harness 官方提供 Settings → Models → Add model provider → Custom model API，可选 OpenAI Chat Completions、Responses、Anthropic Messages；本项目当前仅对应第一个。官方文档还说明 supportsDeveloperRole/maxTokensField 等兼容选项。本地 MVP 尚缺流式输出与完整工具调用，不能据此宣布 DSH Agent 已可用。

CC Switch 是客户端配置与本地路由工具，不替代我们的成员授权/额度/推理服务。其支持的客户端清单与协议随版本变化；Codex/Claude 原生协议与 Chat Completions 不同，转换代理仍要求上游实际支持所需的流与工具语义。

来源：[DSH 模型配置](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/guide/providers.md)、[CC Switch](https://github.com/farion1231/cc-switch)。

## 网络与上线顺序

本机 loopback HTTP 不经过校园局域网；SSH 转发保护远程链路。HTTP 自身不提供加密，校园网也不等于可信。正式站点需域名与有效证书，通过 HTTPS 提供站点/API。

拟议部署：公网客户端 → 云服务器 HTTPS 反向代理与网关 → 校内服务器主动建立的受鉴权加密隧道 → 校内 loopback 推理服务。若云主机直接承载网关，需评估提示词和结果经过云主机的数据边界；也可让云主机仅代理、网关留校内。公网 Web 不持有 Docker socket，控制代理与推理网络分离。隧道/DNS/证书/备份/成员会话/协议与并发验收完成后才开放访问；实际云主机和域名信息仍需私下配置。

同机已有网站时，新站使用新子域名，复用已经存在的 HTTPS 入口，不再让第二个反向代理争抢 80/443。使用独立 Compose 项目名、专属 bridge 网络、独立数据卷和数据库角色、非 root 用户、只读根文件系统（明确可写卷除外）、CPU/内存/PID/日志上限；不使用 host 网络，不挂载 Docker socket，不共用生产环境变量和数据库管理员。只向已有反向代理开放新站 loopback 端口，避免公网绕过；若代理本身容器化，应按现有方案建立最小共享入口网络而非把数据库放入共享网。

若现有网站由 Nginx + systemd 管理，可沿用这种方式为新站单独创建 unit、无登录系统用户、Python 虚拟环境、数据和私有环境目录。利用 NoNewPrivileges、PrivateTmp、ProtectSystem、ProtectHome、ReadWritePaths 和 CPU/内存/PID 限制强化边界。独立 loopback 端口由新增的 Nginx 子域名 server 块代理；验证配置后平滑 reload，保留旧站 unit 与站点配置。目录权限与 systemd 限制须实际验收，独立虚拟环境仅隔离依赖，不能单独隔离文件访问或资源消耗。当前 MVP 的 TrustedHost、Origin 校验和身份会话尚需生产适配，不能将本机启动命令直接反代公开。

先核对三个网站的现有端口、代理类型、资源用量和备份。上线前测试新子域名 Host 路由、证书、重启行为与回滚，并分别回归旧站点。容器共享内核、CPU、内存和磁盘，因此资源限制可降低互相影响，不能承诺物理级完全隔离；若资源不足或要求故障完全隔离，应使用独立虚拟机/主机。公网网关当前缺少正式会话与 Agent 协议，部署配置不能替代这些上线前工作。
